# Exact contact display lookup: scope and acceptance

Based on reviewed upstream 025ff5494df4c9f4a94a7cada787c299f68a95d2. Run `python3 qa/test_contact_identity.py`. It compiles the full production Kotlin resolver and preserved-message store with explicit Android/database/contact-provider substitutes. Extracted production SQL also runs against real SQLite in memory.

Use full namespace-qualified phone/LID/group identifiers. A raw number is not automatically a LID, and a phone hint must not associate an unrelated phone with a supplied LID. Only one explicit jid_map edge to a complete phone JID can supply that mapping. Reject conflicting names and bound reads to 32 rows (queries request one overflow sentinel). PhoneLookup results require matching complete normalized digits, not trailing digits. Local-format contacts with no matching normalized number may remain unresolved; this is intentional rather than assigning another person's name.

The changes preserve database schemas and records. Historical cached names are fallback evidence, not authentication or proof that an event occurred. Existing Activity title/view heuristics remain outside this correction and may still supply unverified display labels. Do not claim the remaining receipt-type classification defects are fixed by a better display name. Device-form JIDs such as user:device and unknown namespaces are not normalized by this policy.

On authorized test accounts, verify exact phone and LID contacts, explicit and conflicting mappings, suffix-collision names, full-number contacts, group subjects, missing/denied/corrupt databases and preserved-message cache conflicts. Test Business and user/work profiles: database lookup must stay within the caller Context and never fall back to user 0 or com.whatsapp from another package. Review CallPrivacy consumers because they share the resolver API. Validate SQLite query plans and long-session costs on real schemas; no CPU/heap/battery improvement percentage is claimed.
